# 警情处置控制台页面规则

## 目标

页面是一张高密度警情处置工作台，不是大屏展示页，也不是产品说明页。

它要支持四类核心活动：

- 接收警情事件并由指挥长决定是否处置。
- 展示 task 成功产出的业务卡片。
- 在同一个侧边区域内切换协作、待办、历史。
- 通过底部指令坞补充指令、上传材料、语音输入或发送命令。

视觉气质应冷静、克制、可靠、可扫读。所有视觉层级都服务于警情、任务、消息、卡片和指令，不使用营销式 hero、大面积渐变、装饰光斑或抽象背景。

## 页面分区

页面由五个固定角色组成：

- 左侧细栏。
- 顶部状态栏。
- 业务卡片工作区。
- 可吸附侧边区域。
- 底部指令坞。

左侧细栏始终固定在最左侧，不跟随侧边区域左右吸附。侧边区域可以收纳、展开、吸附到左侧或右侧。吸附到左侧时，它应位于左侧细栏右侧，不覆盖细栏。

默认比例：

- 业务卡片工作区约占主体宽度 `0.75`。
- 侧边区域约占主体宽度 `0.25`。

切换协作、待办、历史时，只替换侧边区域内部内容。侧边外壳、宽度、吸附方向和收纳状态不应跳动。

## 左侧细栏

左侧细栏是全局模式入口，宽度应保持紧凑，建议 `44px` 到 `56px`。

细栏内垂直放置五个图标控件：

- 协作。
- 待办。
- 历史。
- 语音输入。
- 指令输入。

细栏控件应使用图标、状态条、背景和 hover 反馈表达含义，不在栏内直接展示文字 label。文字只用于 tooltip、`aria-label` 或悬浮提示。

控件行为：

- 点击协作、待办、历史：展开侧边区域并切换对应内容。
- 点击语音输入：显示收音状态样式；第一版只需要麦克风图标和录音中的视觉反馈。
- 点击指令输入：唤出底部指令坞。

当前激活项应有明确但克制的选中态，例如左侧亮条、按钮背景提亮、图标颜色变化。

## 顶部状态栏

顶部状态栏横跨左侧细栏以外的主区域，保持低高度和高信息密度。

左侧放产品身份：

- 紧凑的警务符号或系统图标。
- 产品名使用短标题。
- 不展示“Pi 协同执行原型”等原型说明 label。

中间放当前警情上下文：

- 当前警情名称是顶部最重要的信息。
- 警情编号、区域、时间等辅助信息紧跟标题。
- 文案使用真实业务对象名称，例如“南广场交通事故 · 西侧落客区”。

右侧放全局状态和工具：

- 运行态使用状态灯或小型状态胶囊表达。
- 只保留必要工具，不放通知铃铛。
- 工具按钮使用图标，不使用含义不明的单字。
- 按钮尺寸、边框、hover 和 active 反馈保持一致。

顶部栏不展示功能说明，不承担教学。

## 初始状态和警情入口

页面初始状态下：

- 业务卡片工作区为空。
- 侧边区域默认收纳。
- 底部指令坞默认隐藏。
- 页面显示一个新的警情事件入口。

警情事件入口应像真实系统通知：

- 有警情标题、摘要、时间或来源。
- 有“处置”和“不处置”两个明确动作。
- 层级高于背景，但不遮挡顶部上下文。
- 体积小于主工作台区域。

用户点击“处置”后：

- 警情入口退场。
- 顶部上下文切换为该警情。
- 协作内容进入处置流。
- task 成功后才逐步生成业务卡片。

用户点击“不处置”后：

- 警情入口退场。
- 该警情进入待办或记录为已不处置状态。
- 页面保持待接入或队列查看状态。

## 业务卡片工作区

业务卡片工作区展示 task 成功产出的业务结果。

卡片生成规则：

- 初始为空。
- task 成功且有可视业务结果时生成卡片。
- task 失败时不生成空卡片。
- 成功 task 不需要在协作流额外刷一条长消息；它更新 task 状态和对应卡片即可。

卡片内容必须使用业务语言，不展示工程字段。

卡片标题示例：

- 事发地址定位。
- 处置预案。
- 周边监控。
- 报警人背景。
- 周边警力。

不要在 UI 中出现：

- `map`。
- `text`。
- `media`。
- `table`。
- `json`。
- `card_type`。
- “这是地图卡片”“这是文本卡片”等说明。

卡片头部：

- 左侧是标题和一行业务摘要。
- 右侧只放图形按钮，例如收起、展开、最大化。
- 图形按钮有统一尺寸和视觉反馈。

卡片选中态：

- 选中卡片应有清晰边框或背景差异。
- 选中态联动对应 task 和协作流中的相关节点。

## 侧边区域

侧边区域是可吸附的工作台抽屉。

基础行为：

- 默认收纳。
- 可点击小浮动把手展开。
- 可点击图标按钮收起。
- 可拖拽或点击按钮切换左侧/右侧吸附。
- 收纳后不完全消失，应保留一个小浮动把手。

左右拖动必须有真实交互效果。拖拽侧边区域顶部时，指针移动到视口左半边应吸附到左侧，移动到右半边应吸附到右侧；不是只保留一个静态按钮。

收纳把手设计要求：

- 把手应贴近当前吸附边。
- 在右侧吸附时位于右边缘；在左侧吸附时位于左侧细栏右边。
- 把手应可点击展开。
- 把手可承载当前内容类型的图标状态，但不展示长文字。
- 把手需要有足够精致的 hover、active 和拖拽反馈。

侧边区域内部有三种内容：

- 协作。
- 待办。
- 历史。

三种内容共用同一个侧边区域，切换时整体替换内部内容，不叠加，不打开新面板。

## 协作

协作是一个统一的处置流，不再拆分为“处置动态”和“预案指引”两个上下区域。

处置流承载三类来源：

- 用户。
- 警情消息事件。
- 每一个 task 的状态和失败结果。

协作流按事件生命周期组织，而不是按聊天消息堆叠。

step 标题必须使用 workflow 中的真实业务名称，例如：

- 警情要素识别。
- 基础研判。
- 现场态势展开。
- 出警资源可视化。

不要在 UI 中展示 `step1`、`step2` 这类占位文案。

警情消息通知和处置动态之间必须有一个独立步骤：

- 标题为“根据警情匹配预案指引”。
- 匹配成功时返回 steps，并继续渲染处置动态。
- 返回空时显示“暂未匹配到预案”，且不渲染处置动态整块。
- 该步骤属于系统 / main agent / tool selection 阶段，不是普通 task 行。

警情开始处置时，协作流应展示：

```text
系统头像  警情消息通知
          指挥长张三开始处置：xxx 发生警情...

系统头像  处置动态
          警情要素识别
            执行中  提取出警设备和人员
            等待    ...
          基础研判
            已完成  根据事发地址检索地点
            失败    跟踪出警警车
              task2 fail message
            等待    ...
```

task 状态要求：

- 每个 step 可以包含多个 task。
- task 内部状态可以是 waiting、processing、done、fail、stopped。
- 默认行内不展示可见中文状态 label；状态由 icon、节点形态、边框、透明度和颜色表达。
- 中文状态语义必须保留在数据、`aria-label`、tooltip 或详情层中，例如“等待”“执行中”“已完成”“失败”“已停止”。
- 状态必须通过形状、图标、透明度、边框和颜色共同表达，不只依赖文字。
- 成功 task 只更新状态和卡片。
- 失败 task 展开失败信息。
- 协作流支持滚动，但默认不显示滚动条。

用户主动发指令时：

```text
我  帮我查下神舟路地铁周边监控

系统头像  已开始协查周边监控资源...
```

用户新发出的指令统一显示为“我”，不使用指挥长姓名缩写作为头像文本。

系统回复可以来自 workflow 或 agent，但 UI 不需要暴露 `spawn_agent`、`run_workflow` 等工程实现。

指令坞发送成功后，用户输入内容必须真实追加到协作流中，不只清空输入框。

## 失败 task 处理

失败 task 第一版只需要轻量处理能力。

必须支持：

- 失败 task 行有明显失败状态。
- 失败 task 可被选中。
- 失败 task 可展示失败信息。
- 失败 task 旁边提供重试按钮。
- 点击失败 task 时唤出底部指令坞。
- 指令坞显示引用 chip，例如“引用：跟踪出警警车 · 失败”。

不建议把原 task 内容或失败信息自动写进输入框。输入框只保留用户的新指令。

发送补救指令时，系统 payload 可以附带：

- task id。
- task title。
- 上一次失败信息。
- 原 task 输入摘要。
- 用户新指令。

task 进程已经销毁也不影响 UI 表达；重试或补救应基于 task attempt 记录。

## 待办

待办展示警情事件队列，不展示 workflow 内部 task。

待办是列表。默认每项只展示固定长度摘要；点击选中后，在当前列表项内部展开完整内容。不要打开独立详情页，也不要覆盖卡片区。

待办列表项结构：

```text
[指挥长张三处置中] [警情摘要...]  [协同处置]
[等待处置]          [警情摘要...]  [处置]
[等待处置]          [警情摘要...]  [处置]
[已不处置]          [警情摘要...]  [处置]
```

状态包括：

- 指挥长某某处置中。
- 等待处置。
- 已不处置。

动作包括：

- 协同处置。
- 处置。

状态不能只靠文字表达。应同时使用状态条、状态节点、按钮强弱、透明度或边框表达：

- 处置中：状态条更亮，边框更强，动作按钮为“协同处置”。
- 等待处置：中等对比，动作按钮为“处置”。
- 已不处置：整体弱化，仍可查看完整内容，也允许点击“处置”重新进入协作区。

点击待办标签时，如果侧边区域之前正在显示协作内容，应整体替换为待办列表内容。

点击待办中的“处置”后，应产生真实效果：

- 侧边区域切换回协作。
- 顶部警情上下文切换到该警情。
- 协作流出现新的警情消息通知和指挥长开始处置内容。
- 已不处置警情也支持重新处置。

## 历史

历史展示已处置会话列表。

历史也是列表。默认每项只展示固定长度摘要；点击“处置回放”进入只读回放。

历史列表项结构：

```text
[指挥长张三已处置] [警情摘要...]  [处置回放]
[指挥长李四已处置] [警情摘要...]  [处置回放]
[指挥长张三已处置] [警情摘要...]  [处置回放]
```

历史回放规则：

- 回放是只读状态。
- 不允许继续处置。
- 不允许基于历史直接发指令。
- 点击处置回放后，顶部警情上下文、卡片区、协作流切换到该历史快照。
- 指令坞应隐藏或禁用。

历史视觉语言应更安静，避免和当前处置中的警情竞争注意力。

## 指令坞

指令坞位于页面底部，是浮动输入控制条。

默认不展示。以下情况唤出：

- 鼠标移动到底部区域。
- 点击左侧细栏的指令输入控件。
- 点击侧边区域中的打开指令按钮。
- 选中失败 task。

持久显示规则：

- 鼠标离开底部后，如果输入框没有焦点且没有绑定失败 task，可以隐藏。
- 输入框获得焦点后持续显示。
- 绑定失败 task 时持续显示，直到取消引用或切换上下文。

指令坞结构：

- 引用 chip，展示当前绑定对象。
- 输入框。
- 上传文件按钮。
- 语音输入按钮。
- 发送按钮。

指令坞视觉应参考 Codex App 的 composer：

- 大圆角容器。
- 深色浮层。
- 输入区和按钮在同一个连续容器内。
- 上传、语音、发送按钮是紧凑图标控件。
- 发送按钮应有更强主操作样式。

按钮使用图标控件，不直接用长文字。上传文件、语音输入、发送按钮需要有 tooltip 或 `aria-label`。

输入框要求：

- 单行起步。
- 内容变多时可增高。
- 不遮挡关键卡片操作。
- 占位文案使用真实命令入口语气，例如“输入纠正指令、补充材料或临时协查要求”。

## 语音输入

语音输入第一版只需要表现收音状态。

交互规则：

- 左侧细栏有麦克风图标控件。
- 指令坞内也有麦克风图标按钮。
- 点击后进入收音样式。
- 收音状态可以用脉冲环、声波条、按钮高亮表达。
- 不需要实现完整语音识别链路。

## 选中联动

页面中有三类可选中对象：

- task。
- 协作流节点。
- 业务卡片。

联动规则：

- 选 task，高亮对应协作流节点和卡片。
- 选协作流节点，高亮对应 task 和卡片。
- 选卡片，高亮对应 task 和协作流节点。
- 没有卡片的 task 只联动 task 和协作流节点。

同一组对象使用同一种强调色。强调色不应过亮，不使用闪烁。

## 状态语言

常用状态：

- 待接入。
- 处置中。
- 等待。
- 执行中。
- 已完成。
- 失败。
- 待补救。
- 已停止。
- 不处置。
- 只读回放。

状态表达方式：

- 顶部状态灯表达全局状态。
- task 图标表达执行状态。
- 待办状态条表达队列状态。
- 协作流节点表达事件状态。
- 卡片边框表达选中或异常。
- 历史回放通过弱化指令入口和只读状态表达。

颜色只是一部分。形态、透明度、边框、节点、图标和位置也必须参与状态表达。

## 文案语言

可以出现：

- 警情名称。
- 指挥长姓名。
- 区域。
- 时间。
- task 标题。
- task 失败摘要。
- 用户指令。
- 系统自然语言回复。
- 业务卡片内容。

不要出现：

- `text`、`map`、`media`、`json`、`card_type`。
- `spawn_agent`、`run_workflow`。
- “实时追加”。
- “刚刚更新”。
- “main agent 补救建议”。
- “这是某某模块”。
- “这里展示某某内容”。

## 动效语言

适合使用：

- 新警情事件轻微滑入。
- 侧边区域展开、收起、左右吸附的平滑动效。
- 收纳把手 hover 和拖拽反馈。
- 指令坞底部上浮。
- task 从 waiting 到 processing 的轻微脉冲。
- fail 状态短暂强调后稳定。
- 语音收音时的脉冲或声波。

不适合使用：

- 大幅缩放。
- 长时间闪烁。
- 大面积扫描线。
- 过强霓虹光效。
- 与业务状态无关的装饰动画。

## 窄视口

移动或窄视口不是主要场景，但不能破坏。

窄视口下：

- 左侧细栏保持固定。
- 顶部信息可换行。
- 业务卡片单列排布。
- 侧边区域可作为覆盖抽屉出现。
- 指令坞不造成横向溢出。
- 所有按钮仍可点击。
- 文本不重叠、不溢出容器。

移动端不需要重新设计成独立产品，只需要保持可读、可操作、无明显错位。
